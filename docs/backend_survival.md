# Backend Survival

Отдельный режим `/survival`, кнопка 🖥️ в шапке академии. Вход через обычный аккаунт PANDORA.

Три сценария с разными полями и диапазонами данных: склад орбитальной станции,
телеметрия глубокого космоса и диспетчер аварийных заявок. В каждом 11 последовательных
этапов. Условия, команды и контракт обработчика доступны прямо в режиме.

| Этап | Навык | XP |
| --- | --- | ---: |
| 1 | SSH, venv, запуск, healthcheck | 10 000 |
| 2 | Приём JSON | 15 000 |
| 3 | Ошибки JSON, маршруты и HTTP-методы | 20 000 |
| 4 | Валидация данных | 30 000 |
| 5 | Переменные окружения, токен и размер тела | 40 000 |
| 6 | SQLite, миграция, параметры SQL, идемпотентность | 50 000 |
| 7 | Чтение данных и перезапуск процесса | 65 000 |
| 8 | Конфигурация службы и метрики | 80 000 |
| 9 | Скользящее окно ограничения запросов | 100 000 |
| 10 | Readiness, отказ и восстановление БД | 125 000 |
| 11 | Смешанный поток, повторы, перезапуски, целостность | 150 000 |

Награда за этап точная, без множителей гильдии, событий и дополнительных бонусов ранга.
Она выдаётся только один раз на аккаунт, сценарий, этап и версию кампании. Сброс стенда
сохраняет прохождение и не открывает повторное получение XP. Новые этапы проверяют
также требования предыдущих. Можно повторно проверить уже пройденный этап без награды.

## Как работает стенд

В редакторе есть `app.py`, `.env`, `requirements.txt`, `schema.sql`, `pandora.service`.
`server.py`, `manage.py` и `GUIDE.md` доступны для чтения. В консоли доступны учебные
`ssh`, `python -m venv`, `source`, `pip`, `curl`, `systemctl`, `journalctl`, операции
с файлами и `check`. `help` показывает полный гайд. Внешние пакеты не нужны.

SSH, процессы, порт, установка зависимостей и управление службой эмулируются.
Здесь нет доступа к shell, сети и файлам хоста. Это не полноценный Linux-контейнер
и не измеритель реального RPS. Логика обработчика исполняется ограниченным
интерпретатором синтаксиса Python, а SQL — настоящим SQLite в памяти, отдельно от
`academy.db`. Текст ученика никогда не передаётся в `eval`, `exec` или системную команду.

Поддерживаются функции, условия, циклы, comprehensions, обычные исключения, модуль
`json` и исключения `sqlite3`. Произвольные импорты, классы, async, служебные атрибуты
и распаковка аргументов недоступны. Доступные методы перечислены в `survival_runtime.py`.
Состояние процесса нужно хранить в `state`; постоянные записи — в `db`.
Лимиты кода, числа инструкций, SQL, строк и коллекций ограничивают ресурсы стенда.
Превышение лимита останавливает учебный процесс; перехват `except` его не отменяет.

`handle(request, state, env, db)` возвращает `{'status': int, 'body': JSON}`.
`request` содержит `method`, `path`, исходную строку `body`, `headers`, `client`, `time`.
`db.execute()` принимает SQL и отдельные параметры, возвращает курсор с `fetchone()`
и `fetchall()`; строки представлены словарями. `db.commit()` поддерживается.
В стенде записи сохраняются между запросами автоматически.

Сохранение файлов не заменяет запущенный снимок кода. После изменения нужен
`restart`. Он очищает `state`, сохраняя записи SQLite. Сброс стенда удаляет учебную
БД и возвращает начальные файлы. Данные сценариев и аккаунтов изолированы.

Код сохраняется на сервер автоматически после паузы в наборе. Сохраняются также
выбранный сценарий, открытый файл, этап, позиция курсора, история команд и консоль.
После обновления страницы или повторного входа продолжается тот же стенд.
Локальный черновик привязан к аккаунту и сценарию и подстраховывает при потере сети.
API использует версии рабочего пространства:
устаревшая вкладка получает HTTP 409 вместо перезаписи более нового состояния.

## Проверка и начисление

Проверяющий код находится на сервере. Для проверки создаются новое окружение,
чистая БД, случайные данные и новый токен доступа. Проверяются реальные ответы,
состояние хранилища, работа после ошибок, счётчики, повторы, всплеск запросов,
перезапуски и недоступная БД. Проверяются параметризация SQL и утечки токена.
Это затрудняет подгонку под показанные примеры, но не доказывает отсутствие всех
возможных способов обмана.

API принимает только сценарий, номер этапа и ревизию. Клиент не может передать
успешный результат или сумму награды. Начисление и запись прохождения выполняются
в одной транзакции с уникальным ключом. Есть пауза между проверками и ограничение
числа одновременно работающих проверяющих. Если файлы изменились во время
проверки, её результат не начисляет XP.

Таблицы `survival_workspaces`, `survival_completions` и `survival_preferences`
создаются идемпотентно при обычном запуске PANDORA. Файлы, состояние редактора
и учебные данные хранятся в первой таблице, прохождение и награды — во второй,
последний выбранный сценарий — в третьей. XP также записывается в общий `xp_log`.

## Экспорт

«Скачать проект» выгружает ZIP с файлами ученика и готовым HTTP-адаптером на
стандартной библиотеке Python. Для локального запуска после реализации обработки:

```sh
python -m venv .venv
source .venv/bin/activate
python manage.py migrate
python server.py
```

Адаптер слушает `127.0.0.1` на порту из `.env` и использует локальный `lab.db`.
В экспортированном проекте исполняется обычный Python. Экспорт сам по себе
не является подтверждением прохождения и не начисляет XP.

## Проверки разработки

```sh
venv/bin/python -m unittest discover -s tests -p test_backend_survival.py -v
node --check static/survival.js
```

Тесты покрывают выполнимость всех 33 контрактов, случайные входные данные,
отклонение неправильных решений, границы интерпретатора и SQL, авторизацию,
разделение аккаунтов, защиту файлов адаптера, устаревшие версии, сброс,
параллельное начисление и редактирование во время проверки.
